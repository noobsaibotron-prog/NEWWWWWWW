WHY THIS A/B EXISTS (evidence = Blocco 0, commit 96a5da46)
---------------------------------------------------------
Measured Thinness failure signature (test-only diagnostic, synth-only vs combined,
seeds 11/22/33, checkpoints 0/50/100/200/400/600):
  - PRIMARY cause = TRAINING INSTABILITY / OSCILLATION. logitThin on Thinness fixtures
    swings across checkpoints; the real-sibilance `combined` mix lands it on a LOWER
    band than synth-only -> the per-seed lottery (recall 10/35/17). It is NOT a loss of
    signal (synth-only stays learnable).
  - RULED OUT by the data: dead-ReLU (reluH1/H2 healthy ~0.4-0.6), weight-collapse
    (fc3norm GROWS 1.3->6.0), impossible class, pure data-volume, and lower-LR
    (Blocco 2d negative). Negatives weigh heavily on the Thinness gradient, but this
    ALSO holds in synth-only -> part of the story, not the whole cause.
=> The FIRST production lever must reduce the VARIANCE of the SGD updates (the
   oscillation), NOT rebalance the class or grow the net. Codex order:
   mini-batch averaging (most targeted) first; light weight-decay second.

DESIGN — production training (MLEngine), DEFAULTS PRESERVE CURRENT BEHAVIOUR BYTE-FOR-BYTE
-----------------------------------------------------------------------------------------
  - Add OPTIONAL training params (both default to TODAY's behaviour):
      * miniBatchSize (default 1 == current per-sample SGD). Within an epoch, walk the
        rng(1234)-shuffled order in CONTIGUOUS chunks of miniBatchSize, ACCUMULATE the
        per-sample gradients, apply the MEAN once per chunk (last partial chunk averages
        over its actual size). Same shuffle => deterministic. batchSize=1 reproduces
        today's blob EXACTLY.
      * weightDecay lambda (default 0 == current). applyGradients becomes
        w -= lr*(grad + lambda*w). lambda=0 reproduces today's blob EXACTLY.
  - Implementation note: trainStep currently COMPUTES and APPLIES in one go; mini-batch
    needs trainStep split into "accumulate gradients" + "apply averaged gradients" (a
    contained refactor of MLEngine.cpp:900-1052; the freq-net path batches the same way).
  - KEY SAFETY: defaults == current => the shipped ml_weights.bin and the tests that load
    it (AICorpus, AI-Sweep, BugFixAcceptance) are UNAFFECTED until a candidate is
    deliberately trained with batchSize>1 / lambda>0. These params only change HOW the
    candidate blob is GENERATED (offline/in-test); the inference path, the runtime, and
    the audio path are NOT touched.
  - lr stays FIXED at 0.003 (one cause per change). Mini-batch averaging lowers the step
    NOISE, not the mean step; if a later round needs an lr tweak that is a SEPARATE change.

VERDICT: fixed-lr mini-batch averaging UNDER-TRAINS — NOT a valid test of the stability lever.
Mechanism: mean-averaging + one update per batch moves the weights ~B x less per epoch => at
fixed lr/600 ep it is ~600/B effective epochs (8->~75, 32->~19) => collapse. This does NOT
disprove mini-batch as a variance reducer; it shows it is UNTESTABLE at fixed lr. A fair test
needs lr*B (or epochs*B) — a SECOND variable that breaks the "fixed lr" constraint => requires
its OWN brief/counter-exam before code.
